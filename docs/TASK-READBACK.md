# T06 안내 이해 확인 — 해야 할 일과 남길 결과

이 파일은 공식 항목을 빠짐없이 대조하는 상세 기록이다. 채팅에서는 과제 목표 → 단계별 **해야 할 일·만들 기능·남길 것** → 중요한 검증 기준 표 → 보고서·제출 항목 → 현재 상태로 정리해 보여준다.

확인일: 2026-09-30. 출처: 기존 로그인된 Codex 내장 브라우저의 [공식 T06 화면](https://aleph-omega.vercel.app/cortex?panel=tasks). 전체 설명·완주 체크리스트·카드 1~5·제출 화면을 직접 대조했다.

아래는 공식 안내의 항목명과 순서에 맞춘 요구사항·검증 기준·남길 근거 정리다. 착수 때 작성했고 2026-09-30 제출 직전 최신 전체 설명·카드 1~5·제출 화면을 다시 읽어 대조했다. 각 통과 기준은 공식 기준과 기대 결과이며 실제 수행 결과는 [FINAL-REPORT.md](FINAL-REPORT.md)와 아래 현재 상태에서 구분한다.

## 왜 이걸 하는가

할 일의 완료 체크에서 끝나지 않고, 내가 세운 계획과 실제 행동 사이의 차이가 어떤 방향으로 반복되는지 확인하는 도구를 만든다. 남의 예시 대신 **내 실제 계획·할 일·실행 기록**을 넣고, 돌아보기에서 얻은 결론을 다음 계획에 반영해야 완성이다.

사용자가 정한 기록 주제는 **ALEPH 공부·과제 진행**이다. 계획 → 할 일 → 실행 기록 → 예상과 실제의 비교·돌아보기 → 다음 계획의 개선으로 이어지며 자료는 실제 서버 DB에 저장한다.

## 제출물

공식 안내의 제출물은 다음 네 가지다.

| 제출물 | 준비할 결과 |
|---|---|
| 결과물 주소 | 로그인 없이 열리는 본인의 계획·기록 앱 공개 HTTPS 주소. 실제 본인 자료가 보여야 한다. |
| 소스 주소 | 검증한 최종 소스의 `https://github.com/OWNER/REPO/commit/FULL_COMMIT`. 실제 확인한 40자리 또는 64자리 소문자 전체 커밋을 사용한다. |
| 짧은 확인 4줄 | **어디로 가나요 / 무엇을 하나요(3단계 이내) / 무엇이 보이면 통과 / 안 될 때**. |
| AI 판단 3줄 | **AI에게 맡긴 일 / 내가 판단한 일 / AI 말을 안 들은 일**. 실제 판단을 쓰며 마지막 항목이 없으면 실제 이유를 적는다. |

실제 제출 화면에서는 결과물 URL과 소스 URL을 모두 필수로 안내하고 확인 파일은 선택이다. 모든 증거 화면을 필수 첨부라고 해석하지 않는다. 공개 결과물·소스 URL은 새 시크릿 창에서 인증 없이 열려야 한다. 별도 해시값 입력란은 없다.

전역 접수 안내의 근거 하나 이상 접수 가능과 T06 완성 기준 충족은 구분한다. 확인법·판단은 입력 시 각각 1,500자 이내이며 선택 파일은 최대 10개·합계 8MB 안내를 따른다.

## 완주 체크리스트

아래 다섯 가지는 공식 완료 조건이다. 실제 구현·검증 결과는 보고서와 현재 상태에 연결한다.

1. 계획 → 실제로 한 일 → 돌아보기의 자료가 실제 서버 데이터베이스로 연결된다.
2. 본인이 실제로 세운 계획·할 일·실행 기록이 앱에 들어 있다.
3. 집계 숫자를 누르면 그 숫자에 기여한 기록으로 이동할 수 있다.
4. 아직 로그인이 없다는 안내가 첫 화면에 표시된다.
5. 최종 소스, 스크립트 삽입 가능성, 비밀값 노출, 외부 공개 여부를 실제로 확인한다.

## 1단계 · 계획 세우기

### 하는 일

실제로 진행하는 일 하나의 계획을 세우고, 계획 ID·기간·우선순위·성공 기준·예상 시간을 서버에 저장한다. 같은 계획을 수정해도 변경 전 내용을 별도 이력으로 보존한다.

### 첫 행동

사용자 본인의 **ALEPH 공부·과제 진행** 계획 하나를 정하고 실제 내용을 입력해 저장한다. 저장한 계획을 한 번 수정해 현재 내용과 수정 전 내용을 확인한다.

### 통과 기준

검증 기준: 저장 전후 계획 ID와 기간·우선순위·성공 기준·예상 시간을 대조한다. 수정 후에도 같은 계획 ID가 유지되고, 수정 전 내용과 현재 내용을 각각 확인할 수 있어야 한다. 이전 내용은 덮어쓰지 않는다. (T06-C04~C08)

### 막히는 지점과 확인 순서

1. 이력을 별도로 저장하는 구조가 있는지 확인한다.
2. 현재 값과 이전 값이 분리되어 있는지 확인한다.
3. 수정 전후 같은 계획 ID를 사용하는지 확인한다.

### 남길 것

- 사용자의 실제 계획이 저장된 화면과 기록.
- 같은 계획 ID의 수정 전·후 내용을 보여 주는 이력 화면과 기록.

## 2단계 · 할 일 다루기

### 하는 일

계획에 연결된 할 일을 만들고 수정·완료·진행 중으로 되돌리기·삭제를 구현한다. 마감일·우선순위·태그·예상 시간을 저장하고 검색·필터·정렬과 동률 처리 규칙을 화면에 표시한다.

### 첫 행동

1단계의 실제 계획에 연결할 실제 할 일을 작성한다. 최종 실제 자료 기준은 할 일 **5개 이상**이므로 사용자가 실제로 해야 하는 일로 채운다. 각 할 일의 마감일·우선순위·태그·예상 시간을 정한다.

### 통과 기준

검증 기준: 만들기·수정·완료·되돌리기·삭제를 각각 실행하고 저장 결과를 대조한다. 검색·필터 결과가 조건에 맞아야 한다. 같은 정렬 값이 있는 자료도 화면에 밝힌 동률 처리 규칙대로 일정한 순서를 유지해야 한다. (T06-C09~C20)

### 막히는 지점과 확인 순서

1. 화면에 정렬 기준이 표시되는지 확인한다.
2. 같은 값일 때 순서를 결정하는 기준을 확인한다.
3. 서버와 화면 중 어디에서 필터·정렬하는지 확인한다.

### 남길 것

- 만들기·수정·완료·되돌리기·삭제의 실제 동작이 확인되는 화면과 기록.
- 검색·필터·정렬 결과 및 화면에 표시된 정렬·동률 처리 규칙.

## 3단계 · 실제로 한 일 적기

### 하는 일

할 일에 연결된 실행 기록을 계획과 분리해 저장한다. 실행 기록에는 시작 시각·끝난 시각·실제 소요 시간·막혔던 이유를 남긴다. 반복 완료 요청이 중복 기록과 중복 집계로 이어지지 않게 한다.

### 첫 행동

사용자가 실제로 수행한 실행 하나를 해당 할 일에 연결해 입력한다. 저장한 실행과 원래 계획을 함께 확인하고, 완료 버튼을 연달아 두 번 눌러 중복 처리 검사를 시작한다.

### 통과 기준

검증 기준:

- 실행 필드가 해당 할 일에 연결되어 저장되고, 실행 추가 전후 원래 계획 값이 같아야 한다.
- 미완료 할 일에 같은 완료 요청을 두 번 보내도 완료 기록은 **1건**이어야 한다.
- 해당 완료 처리로 회고의 완료 수는 정확히 **1만 증가**해야 한다. 두 번째 동일 요청이 추가 기록이나 추가 증가를 만들면 실패다. (T06-C21~C27)

### 막히는 지점과 확인 순서

1. 같은 요청을 식별하는 방법을 확인한다.
2. DB의 중복 방지 제약을 확인한다.
3. 버튼 비활성화만으로 중복을 처리하는지 확인한다.

요청 식별 키와 DB 제약은 안내의 점검 방향이다. 구현에서는 요청 영수증·할 일 주기 고유 제약·트랜잭션 잠금을 사용했고 실제 PG에서 중복·재생을 검증했다.

### 남길 것

- 실행 기록과 연결된 할 일을 함께 확인할 수 있는 화면·기록.
- 실행 추가 전후 원래 계획이 유지된 대조 결과.
- 두 번 요청해도 완료 기록 **1건**, 완료 집계 증가량 **+1**인 실제 검사 결과.

## 4단계 · 돌아보기, 그리고 다음 계획으로

### 하는 일

선택한 계획의 기간에 대해 계획 수·완료 수·지연 수·막힘 수·예상 시간·실제 시간·시간 차이를 보여 준다. 지표를 클릭하면 계산에 기여한 기록을 확인할 수 있게 한다. 회고에서 개선 한 가지를 정해 다음 계획으로 이어간다.

### 첫 행동

저장된 실제 할 일과 실행 기록을 대상으로 집계를 계산한다. 집계 지표를 눌러 기여 기록을 확인한 뒤, 사용자 본인이 판단한 개선 한 가지를 다음 계획에 반영한다.

### 통과 기준

검증 기준: 아래 규칙으로 원기록을 직접 세거나 합산해 화면의 집계와 대조한다. (T06-C28~C33, C83)

| 항목 | 공식 계산 규칙과 기대 결과 |
|---|---|
| 계획 수 | 해당 계획에 딸린 삭제되지 않은 할 일 수와 같아야 한다. 계획 문서 개수를 세지 않는다. |
| 완료 수 | 위 할 일 중 현재 완료 상태인 수와 같아야 한다. 과거 완료 버튼 클릭 횟수를 세지 않는다. |
| 지연 수 | 미완료이고 마감일이 Asia/Seoul 기준 오늘보다 이전인 할 일 수와 같아야 한다. 완료된 할 일은 제외한다. |
| 막힘 수 | 실행 기록에 막힌 이유가 하나라도 적힌 할 일 수와 같아야 한다. 같은 할 일의 막힌 실행이 여러 개여도 해당 할 일은 한 번 센다. |
| 예상 시간 | 현재 집계 대상 할 일의 예상 시간 합계와 같아야 한다. |
| 실제 시간 | 그 할 일에 연결된 실행 기록의 실제 시간 합계와 같아야 한다. |
| 시간 차이 | **실제 시간 − 예상 시간**과 같아야 한다. 대상 자료가 없으면 합계는 **0**이다. |

각 지표를 눌렀을 때 계산에 기여한 기록이 확인되어야 한다. 회고의 개선 **한 가지**가 다음 계획으로 이어진 결과도 확인한다.

### 막히는 지점과 확인 순서

1. 예상 시간이 저장되는지 확인한다.
2. 실제 시간이 저장되는지 확인한다.
3. 같은 단위로 실제 시간 − 예상 시간을 계산하는지 확인한다.

### 남길 것

- 실제 자료로 계산한 집계 화면.
- 집계 지표를 눌러 확인한 근거 기록.
- 원기록으로 직접 계산한 값과 화면값의 대조 결과.
- 개선 한 줄이 다음 계획으로 넘어간 결과.

## 5단계 · 내 것으로 채우고, 잃지 않게

### 하는 일

본인의 실제 자료로 앱을 채우고 계획·할 일·실행·회고를 실제 서버 DB에 저장한다. 공개 사실 안내, 전체 내보내기, 새로고침 후 유지, 실제 DB 계약, 문자열 표시 안전성, 비밀값 미노출을 갖춘 최종 소스를 준비한다. T06에는 회원가입·로그인·인증을 붙이지 않는다.

첫 화면에 다음 안내를 그대로 표시한다.

> 지금은 로그인이 없어 링크를 아는 사람은 누구나 볼 수 있습니다. 남이 봐도 괜찮은 내용만 넣으세요

### 첫 행동

사용자 본인의 실제 계획 **1개 이상**, 해당 계획의 실제 할 일 **5개 이상**, 실제 실행 기록 **3개 이상**을 입력한다. 공개해도 되는 본인 내용으로 제한하고 다른 사람의 이름·연락처와 민감한 내용을 넣지 않는다. 이 자료로 회고를 확인한 뒤 전체 자료를 내보내고 새로고침 전후를 대조한다.

### 통과 기준

검증 기준:

- 실제 사용자 자료가 계획 **≥1**, 할 일 **≥5**, 실행 기록 **≥3**이어야 한다. 회고에서 실제 자료로 계산한 0이 아닌 값이 확인되어야 한다. 모든 지표가 전부 0인 상태로 끝내지 않는다.
- 실제 서버 DB에 계획·할 일·실행·회고가 저장되어야 한다.
- 전체 자료를 파일 **1개**로 내보내고 원저장 자료와 대조한다.
- 새로고침 전후 **ID·날짜·값·단위가 같아야** 한다.
- `contracts/pds-schema-v2.json`의 표·항목·관계·날짜 규칙이 최종 실제 DB와 일치하며 최종 소스에 포함되어야 한다.
- 저장한 스크립트 모양 문자열이 문자로 표시되며 실행되지 않아야 한다.
- 브라우저 코드·배포 파일·네트워크 응답·콘솔·Git 기록에서 비밀키 원문이 노출되지 않아야 한다.
- 첫 화면에서 정확한 공개 안내가 보여야 한다.
- 결과물·소스 URL이 새 시크릿 창에서 인증 없이 열리고 실제 전체 커밋이 확인되어야 한다.
- 제출 확인 4항목과 AI 판단 3항목을 실제 검사·사용자 판단에 맞게 준비한다. (T06-C01, C34~C36, C57~C60, C78~C82)

### 막히는 지점과 확인 순서

1. 자료가 실제 서버 DB에 저장되는지 확인한다.
2. 날짜·시간대 규칙을 확인한다.
3. 저장과 화면 표시의 숫자 단위가 같은지 확인한다.

### 남길 것

- 본인의 실제 계획·할 일·실행 기록이 들어 있는 화면과 기록.

## 과제에서 지정하지 않은 구현 선택

- Node.js 24·로컬 SQLite·운영 Supabase PostgreSQL·Vercel을 사용했다. 특정 서비스·프레임워크 사용은 공식 지정이 아니다.
- 시간 단위를 분으로 통일한 것은 구현 선택이며 공식 지정은 아니다. 저장·표시·계산에서 같은 단위를 사용한다.
- DB의 영문 테이블 이름은 구현 선택이다. 계약 파일에는 실제 구현을 기록한다.
- 전체 내보내기 파일은 **1개**여야 하지만 확인한 카드에는 JSON·CSV·ZIP 중 하나를 특정해 지정하지 않았다.
- 화면 수·화면 이름·캡처 파일명·보고서 형식·제출 첨부 수를 추가 필수 조건으로 만들지 않는다.
- 사용자 실제 기록과 기능 검사용 합성 시험값을 구분한다.
